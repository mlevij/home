## Part 1: Full weather parameters (Air Temp / Humidity / Wind / Solar Radiation charts)

User wanted all available CoAgMET/RAWS/SNOTEL weather data (not just texture/pH) surfaced, not as a side-panel snapshot list (my first design) but as **new charts** matching the existing VWC/Temp/Precip/Snowpack pattern wherever the data is genuinely time-series — user corrected me on this explicitly mid-plan.

**Built:** four new chart sections (Air Temperature, Humidity, Wind, Solar Radiation) with `buildAirTempChart`/`buildHumidityChart`/`buildWindChart`/`buildSolarChart`, following the exact existing chart-function pattern. Wired into all three networks' branches of `loadSoilMoisture()`:
- **CoAgMET**: all fields already sitting in the already-fetched `coagmet-daily.json` (`tAvg/tMax/tMin`, `rhMax/rhMin`, `windRun/gustSpeed`, `solarRad`) — zero new fetches. `windRun` (a daily total distance in miles, not a speed) divided by 24 to get a comparable avg-mph line alongside `gustSpeed` on the same Wind chart axis.
- **RAWS**: extracted from the already-fetched NIFC `Observations` array per click (`ATF`, `RHP`, `WSM`/`WSMP`, `SRW`) — zero new fetches.
- **SNOTEL**: added `TAVG,TMAX,TMIN,RHUM,WSPDV,WSPDX,WDIRV,SWINV` to the existing single AWDB `elements` list — one extra request parameter, not a new call. Not every SNOTEL station reports every element; each chart independently shows/hides with its own status message, same graceful-omission pattern as everywhere else on this site.

**Sidebar-only (not charted)**: wind direction (a compass value, doesn't line-chart meaningfully) and CoAgMET's reference ET (a single specialized stat, RAWS/SNOTEL have no equivalent).

Verified all of this via a subagent driving real headless Chrome (Playwright + `channel="chrome"`) against a local `python -m http.server` — this pattern (no Node/npm available in this environment) became the standard verification method for the rest of the session. CoAgMET/SNOTEL/Zentra all verified with real data; RAWS's live NIFC endpoint (`weather.nifc.gov`) turned out to be unreachable from the sandbox used for browser verification all session (confirmed via direct `curl`, connection just hangs) — RAWS's *code path* was verified structurally (same pattern as the other three, correct graceful-degradation messaging) but never with real live data this session.

## Part 2: Wind rose (hand-rolled SVG)

User asked for a "wind rose" for the wind-direction sidebar row instead of plain text — given the choice between a simple compass-dial (single latest reading) and a true statistical wind rose (direction/speed distribution over the selected time period), user chose the full wind rose.

Built entirely by hand (no charting library — Chart.js has no native radial-stacked-bar type): 8 compass-direction sectors × 5 speed bins (`<5, 5-10, 10-15, 15-20, 20+ mph`), stacked annular-sector SVG paths (`annularSectorPath()`, `polarPt()` helpers), radius encodes % frequency, same spirit as the sidebar's existing hand-rolled pH-scale widget. Per network:
- **CoAgMET**: bins the daily peak-gust direction/speed (`gustDir`/`gustSpeed`) over the span — coarser (one reading/day) but real.
- **RAWS**: bins every sub-hourly `WDD`/`WSM` observation — highest resolution of the three.
- **SNOTEL**: pairs `WDIRV`/`WSPDV` by date (`pairByDate()` helper — AWDB elements don't always report the same days for both).

Verified geometry correctness against raw data, not just visually — a verification subagent reverse-computed each rendered wedge's angle/radius from the SVG path math and cross-checked it against `coagmet-daily.json`'s actual `gustDir`/`gustSpeed` values for Lamar (LAM01) at both 7-day and 30-day spans; matched to sub-pixel precision.

## Part 4: SNOTEL soil data rebuild — texture/pH for the first time, from two real sources

Original ask: "populate the SNOTEL table so texture/pH populate the left panel" like CoAgMET/RAWS already do. `SNOTEL_SOIL` previously had only Saxton-Rawls `wp/srFC/sat/cf` for 47 stations, no texture/sand/silt/clay/pH/EC — sourced from `SNOTEL-data-for-Levi.xlsx`.

**Backstory this session surfaced:** re-investigated two old R scripts (`R_colorado_snotel_lab_data_linkage.R`, `R_CO_SNOTEL_Lab_Data.R`) sitting in the user's SNOTEL OneDrive folder — these join real KSSL lab pedon data (via AWDB's `pedonCode` field → NRCS Soil Data Access → `fetchLDM()`) for a 17-station "force list," but use **nearest-midpoint** horizon-to-sensor-depth matching, which the user explicitly rejected as wrong ("doesn't make sense to put the sensor in another soil type just because it's closer") — the correct rule, confirmed by the user, is **containment** (does the horizon's depth range actually contain the sensor depth).

Also found AWDB's live `pedonCode` field is **unreliable** — it disagreed in both directions with the user's own authoritative `SItes_with_Soil Characterization.xlsx` (which has real lab pedon numbers recorded directly). The authoritative list is 17 CO stations, not the 15 a naive AWDB query would suggest.

**Final data sources used** (Python, not R — no R runtime in this environment; used `py -3.10` since that's the interpreter with `osgeo`/GDAL already installed, not the default `py` 3.13):
- **16 stations**: `SNOTEL Soil Data CO SMM.xlsx`'s `Sensor_Summary` sheet — already correctly containment-snapped per the user's own earlier work with Claude Desktop, confirmed reliable. Name-matched to AWDB `stationId` (mapping table built and verified this session). One 17th station (Buckskin Joe/938) has no pre-built spreadsheet row and fell through to SSURGO.
- **34 more stations**: SSURGO (`CO_SSURGO.gpkg`) dominant-component horizons, containment-snapped to each station's **real** sensor depths (fetched from AWDB the same way `loadSNOTEL()` already does, not guessed). WP/FC computed via literal Saxton-Rawls (2006) equations ported from the R script, matching methodology exactly.
  - **Bug caught and fixed mid-build**: initially read Sat from SSURGO's own `wsatiated_r` field, but mixing that with independently-computed Saxton-Rawls WP/FC produced physically impossible `Sat < FC` rows for some horizons (two different models don't agree). Fixed by deriving Sat via the actual Saxton-Rawls saturation formula (the `S-33` term from the same paper) from the same sand/clay/OM inputs as WP/FC, guaranteeing internal consistency. Verified: all 197 output records now pass `WP ≤ FC ≤ Sat`.
- **65 stations excluded** (no soil sensor at all — confirmed only 53 of 118 CO SNOTEL stations have one) and **3 more excluded** (sensor exists but no SSURGO mapunit polygon at their exact coordinates: Brumley/369, Buckskin Joe/938, Grizzly Peak/505) — user explicitly chose not to extend scope to cover these ("50 sensored stations only" and "leave them out for now" via `AskUserQuestion`).

**Result:** `SNOTEL_SOIL` grew from 47 → 50 stations, now with full texture/sand/silt/clay/pH/EC/%C/coarse-fragment data alongside WP/FC/Sat, each depth tagged `src:'measured'` or `src:'modeled'`. Per user's explicit choice (`AskUserQuestion`), the table shows **real measured values where they exist**, tagged with a small green "lab" superscript next to WP, rather than uniformly recomputing Saxton-Rawls everywhere for column-header consistency.

**Two follow-on bugs found by browser verification and fixed:**
1. Sidebar texture label did `textContent = d.tex` with no fallback — went blank (not "—") for measured stations missing a texture value (e.g. Cascade #2, whose lab data has no texture on any depth). Fixed to use the existing `fmt()` helper, matching the table's own convention.
2. Data-panel subtitle always said "...Saxton-Rawls modeled values" even for now-measured stations — added a `snotelSourceLabel(depths)` helper that reads each depth's `src` and says "KSSL lab-measured values" / "Saxton-Rawls modeled values" / a mixed label as appropriate.

**Not a bug (investigated, explained to user):** Schofield Pass appeared to show a texture in the sidebar but not the table. Root cause: the sidebar's Sand/Silt/Clay doughnut renders fine off real particle-size data (which this station has) even when no *texture-class name* was recorded (which it doesn't have) — the actual "—" label was just easy to miss sitting under a full colorful chart, unlike the table's stark bare "—" cell. Fixed by making the sidebar spell it out explicitly ("No texture class recorded," italicized) when `d.tex` is missing, rather than a bare dash.

**Also fixed same session:** `buildVwcChart()`'s WP/FC/Sat zone-shading always used `depths[0]` (the shallowest depth) for the chart's colored background zones, even when that specific depth had no wp/fc/sat data. Surfaced by SNOTEL "Arapaho Ridge" (stationId 1030): its 2" depth is an organic "MPM" horizon with no sand/clay to compute Saxton-Rawls from, so `wp`/`fc` came back `undefined`, and the yellow "Sat" zone (`yMin: fc, yMax: 100`) filled the *entire* chart in solid mustard instead of not rendering — caused by the annotation-render condition checking only whether the `depths` array itself was truthy, not whether real data was found. Fixed both: `d0` now searches for the shallowest depth that actually has complete `wp`/`srFC`/`sat` (falling through to deeper depths), and the annotation block is gated on `d0` being found. Confirmed via this fix that `buildVwcChart` has only ever used a single depth's values for shading, never an aggregation — this was a direct user question, answered and then immediately explained the bug that question surfaced.

## Part 5: Search & Filter sidebar card (new feature)

New card above "Map Layers": text search (any ID/name across all 4 networks) + Network/Texture/County/HUC dropdowns + Clear filters + live "N of M shown" count.

**Core new infrastructure**: nothing previously tracked `{marker, station}` pairs — every marker was built inline in a `forEach` and only survived as a closure. Added `markerRegistry` + `registerMarker()`, called from all four networks' marker-creation loops (CoAgMET/RAWS/SNOTEL/Zentra). Filtering (`applySearchFilter()`) reuses the exact `layer.addLayer()`/`removeLayer()` mechanism the existing network toggle buttons already use, just at per-marker granularity — composes for free with those buttons (verified: filtering to one network, then cycling another network's toggle off/on, doesn't resurrect filtered-out markers).

**Real bug found and fixed during verification**: county filtering silently failed to match the same physical county across networks — CoAgMET/Zentra store `"Chaffee County"` (from the FCC Area API lookup, `station-counties.json`), while SNOTEL/RAWS store bare `"Chaffee"` (native AWDB/NIFC fields). Added `normalizeCounty()` (strips a trailing " County" suffix) applied only at the registry/filter layer — the sidebar's own display text (`coagmetMeta()`'s "Chaffee County, CO") is untouched. Verified selecting "Costilla" now correctly returns both CoAgMET and SNOTEL stations together.

**Also fixed while building this**: RAWS never had a persistent raw county field (only a formatted `"X County, ST"` display string) — added `countyRaw: s['County']` capture at marker-creation time so RAWS can actually participate in county filtering.

**Eco Region and Land Use** were initially added as HTML-commented-out placeholder `<select>`s (no data source found in the codebase at the time) — confirmed via DOM inspection that the comments render cleanly with no leaked/broken elements. Land Use has since been un-commented (see Part 6 — a data source turned up).

**`#stationCount` relocated**: user noticed the "Loading CoAgMET..." text (previously at the bottom of "Map Layers") was getting buried now that Search & Filter is the first card. Moved it into the bottom of the Search & Filter card instead, right below the filter count / Clear filters row. Pure DOM move, no JS changes (same `id`, `getElementById` unaffected by location).

## Part 6: HUC6/8/10/12 + Land Use — real data found in `Master List.gdb` (verified, two bugs found and fixed)

User asked whether I had (or needed) a HUC/watershed boundary layer for the HUC filter, which at that point only worked for SNOTEL (AWDB's own metadata has a native `huc` field, no spatial join needed). Checked the ArcGIS `Resources` folder first rather than assuming — no dedicated HUC/WBD layer there (`USGS Water-2025` turned out to be Census TIGER/Line water bodies, not watershed boundaries), but *did* find `land_use_land_cover_NLCD`'s real Colorado-clipped NLCD raster + a NASS Cropland layer, both unrelated-but-relevant finds mentioned to the user.

**User then said to check `Master_List.gdb`** — this turned out to be a goldmine: 375 layers, including `HUC08_CO`/`HUC08_CO_26913`/`HUC08_4326`, `HUC06_CO_26913`, `HUC10_Watersheds`/`_26913`, `CO_HUC10_Watersheds_26913`, `HUC12`/`CO_HUC12_26913`, and critically **`Master_List_with_HUC`** (769 rows spanning CoAgMET/RAWS/SNOTEL/other networks) which already has `HUC08`/`HUC08_NAME`/`HUC06`/`HUC06_NAME` **pre-joined per station** with 100% coverage across all three of our networks (94 CoAgMET, 151 RAWS, 114 SNOTEL had HUC08) — a real upgrade over the SNOTEL-only coverage that existed before. It also carries `Land_Use_1/2/3` per station (real curated categories, e.g. "Cultivated Crops," not raw NLCD codes) and `Soil_Texture`/`SOC`/`Clay`/`Soil_pH` columns (noted to the user as a separate, bigger question — a possibly-different soil-data source than what's already wired in — explicitly not touched or conflated with this task).

HUC10/HUC12 aren't in that table, so built `export_huc_landuse.py`: reads `Master_List_with_HUC` directly for HUC6/8 + Land Use, then does a point-in-polygon spatial join (reprojecting each station's lat/lon into EPSG:26913, the user's own canonical CRS, to match `CO_HUC10_Watersheds_26913`/`CO_HUC12_26913`) for the two missing levels.

**One join-key bug caught and fixed mid-script**: `Master_List_with_HUC`'s `ID` field is mostly **null for RAWS** rows (only 51 of 150+ populated) — the reliable RAWS key in that table is `Station` (the uppercase name, e.g. "BAILEY"), which matches this site's own RAWS `name` field exactly. CoAgMET/SNOTEL's `ID` field is reliable and matches this site's own join keys directly. Fixed the script to use the right field per network — RAWS coverage jumped from 51 → 150 stations once corrected.

**Final export**: 94 CoAgMET + 150 RAWS + 109 SNOTEL stations, 100% HUC10/HUC12 spatial-join success (zero misses), 13 distinct HUC6 / 60 HUC8 / 175 HUC10 / 238 HUC12 values, 24 distinct Land Use categories. Written to `soil/huc-landuse.json` (copied from the scratchpad export).

**UI design decision** (asked via `AskUserQuestion` given HUC12's 238 options would clutter 4 separate dropdowns): user chose a single HUC dropdown + an adjacent small "Level" selector (6/8/10/12, defaults to 8) that determines which value set populates the main dropdown — implemented as `rebuildHucOptions(level)`, called on page load once data resolves and again whenever the level selector changes (also resets the HUC value selection, since a HUC8 code isn't meaningful at HUC12).

**JS wiring**:
- `registerMarker()` no longer takes a `huc` param — every entry now gets `huc: {6,8,10,12}` (all null initially) + `landUse: []`, populated either immediately (if `huc-landuse.json` already resolved by the time the station registers) or via a one-time patch pass over `markerRegistry` once the fetch resolves (`applyHucLandUse()`) — covers both load-order cases (CoAgMET/Zentra register early, RAWS/SNOTEL register late over 60-90s).
- `applySearchFilter()` updated to read `filterHucLevel` + `filterHuc` + `filterLanduse`, matching `entry.huc[hucLevel] === huc` and `entry.landUse.includes(landuse)`.
- Removed the now-dead `huc: s.huc || null` / `huc: null` arguments from all 4 `registerMarker()` call sites (CoAgMET/Zentra/RAWS/SNOTEL) since the param no longer exists on that function.
- Land Use `<select>` promoted from HTML-commented placeholder to live, using the same incremental `addFilterOptions()` pattern as County/Texture (flat single-level list, no rebuild-per-level needed the way HUC does).
- Eco Region stays commented out — still no data source found for it anywhere in the user's local GIS resources checked so far.

**Two real bugs found by browser verification (a 98-second unattended monitor run) and fixed:**
1. **Stale HUC dropdown.** `rebuildHucOptions()` was only ever called from the `huc-landuse.json` fetch's own `.then()` (which resolves before RAWS/SNOTEL finish registering, over 60-90s) and the level-change handler — never re-run once those two networks actually finished loading. Proven with a timed check: the HUC8 dropdown froze at 45 options when the true full-registry count was 61. Unlike `addFilterOptions()` (used for county/texture/land use), which is called incrementally inside `registerMarker` on every single registration and so grows correctly as networks stream in, `rebuildHucOptions()` had no equivalent. Fixed by adding a `rebuildHucOptions(document.getElementById('filterHucLevel').value)` call at the end of both `loadRAWS()` and `loadSNOTEL()`, alongside their existing `applySearchFilter()` calls. Re-verified: dropdown count now correctly grows 45 → 58 → 61 over the load window, exactly matching the true registry count at each point (not just "bigger than before").
2. **RAWS name mismatch.** The static `RAWS_NETWORK` fallback list has `"FT CARSON"` (no period) while `soil/huc-landuse.json`'s RAWS keys (sourced from `Master_List_with_HUC`'s `Station` field) use `"FT. CARSON"` (with period) — so that one station's HUC/Land-Use data silently never joined (`huc` stayed all-null, `landUse` stayed empty). Fixed with a small `RAWS_HUC_KEY_ALIASES` map that `applyHucLandUse()` checks for RAWS entries before doing the lookup — same pattern already established by `RAWS_SOIL_KEY` for a different join (lab-sample matching). Re-verified: all 50 static-fallback RAWS stations now join with zero misses (`FT CARSON` confirmed to have real values at all 4 HUC levels plus non-empty land use post-fix).

Brace/paren/bracket balance re-checked after every edit this session (no headless-browser syntax checker available — `py -3.10`'s regex-based balance count against the file's single `<script>` block was the standing verification method throughout, same as prior sessions).
