### API mechanics learned (ZENTRA Cloud 1.0, API v3 — `get_readings` endpoint)
- Auth: `Authorization: Token <key>` header, not a URL param.
- Response shape: `{"pagination": {...}, "data": {sensor_name: [{"metadata": {...}, "readings": [...]}]}}`. Same device can have multiple channels under one sensor name (e.g. two `Soil Temperature` entries for two different ports/depths) — code must key on `(sensor_name, port_number)`, not just sensor name.
- Rate limit: 60 calls/min total, **1 call/min per device**. Hit a real 429 mid-session; fixed by parsing the "expires in N seconds" message from the error body and auto-retrying instead of crashing.
- **Pagination bug found:** requests longer than ~7 days silently truncate to just the current partial day's data on page 1, with a `next_url` for more. Tried following `next_url` — it returned empty pages for date ranges later confirmed (via a direct single-call probe) to actually have real data. Root-caused as unreliable, not real data gaps. **Fix:** stopped trusting `next_url` entirely; instead self-chunk requests into explicit ≤7-day windows (confirmed reliable), issue one call per chunk, merge and de-dupe by `mrid`.
- v4 checked as an alternative — confirmed functionally identical to v3 (docs literally say v3/v4 docs are the same, swap the version number in the URL). No device-list/discovery endpoint exists in either version; device serials have to be already known (from the dashboard) before calling `get_readings`. Trick for cheap metadata-only checks on an already-known device: request a very narrow date window — full `metadata` block still comes back with ~0-1 readings.

### Pipeline built (in `Zentra/`)
- `fetch_zentra.py` — single-window fetch + compact summary table (superseded for production use by the chunked version below, kept as the simplest example/reference).
- `diagnostic_check.py` — single-call narrow-date-range probe; used to catch the pagination bug.
- `fetch_new_sites.py` — the working version: 7-day-chunked fetch for ECRC + RP-Pasture, per-device rate-limit tracking, 429 retry, de-dupe by mrid, saves `latest_{device_sn}.json`. Confirmed both sites have genuinely different sensor suites (ECRC has extra channels like `Drop Counts`/`Spoon Tips`/`EC`/TEROS 12 that RP-Pasture doesn't) — code keeps results in per-device dicts rather than assuming a shared channel list.
- `weekly_summary.py` — reads the already-fetched local JSON (no API calls), resamples to weekly mean/min/max/count per channel via pandas, saves `weekly_{device_sn}.json`. Validated output looks sane — both sites show a clear, consistent moisture jump across multiple ports the week of 6/28, likely a real rain event.

### Architecture decided for production version (not yet built)
- ZENTRA API key can't go in client-side JS (unlike the RAWS live fetch, which uses NIFC's open-CORS API) — has to be a scheduled backend job, same shape as the existing `update-soil-moisture.yml` GitHub Action for CoAgMET: runs on a cron (e.g. nightly), key lives as a **GitHub Actions secret** (separate from repo code/history, not public even in a public repo), writes a static JSON file, commits/pushes, site JS just fetches the static file.
- Once a baseline dataset exists, production fetches should be **incremental** (from last-saved timestamp forward, not a fixed rolling window) — avoids the multi-page/rate-limit pain entirely for day-to-day runs, since a daily delta is only ~24 readings/channel, well within a single page.
- Output granularity: leaning weekly by default per user, two-tier design (rolling raw window for "live" chart, matching the existing CoAgMET/RAWS pattern, + longer-term weekly/monthly aggregates) still the working plan, not finalized.
