## Part 4: PRC duplicate-mukey bug — the real investigation

**Symptom:** After building `PRC_Official_unproj` and running the standard Project → Clip pipeline, `PRC_Soils` showed two separate rows for `musym = WIA` / `mukey = 94223`, unlike every other station (verified `ARDEC_Soils`: 16 rows, 16 unique mukeys, zero duplicates).

**Ruled out, in order, each with direct verification (not guessing):**
1. Stale attribute table display in Pro — ruled out via direct `arcpy` query showing genuinely correct, populated SSURGO attributes early on (areasymbol `CO009` = Baca County).
2. Source SSURGO data itself having duplicate rows for mukey 94223 in `mupolygon_all_joins_26913` — ruled out; confirmed exactly one row.
3. `Intersect` inherently splitting disconnected/multipart geometry into separate output rows (two wrong theories in a row: first "boundary parts don't touch," then "a given mukey's clipped output ends up disconnected") — both disproved by comparing directly against ARDEC: `ARDEC_Official_26913` is one row with `partCount=3` (three non-touching parcels correctly dissolved into one multipart feature), and ARDEC mukeys (e.g. `497724`, confirmed by user as one that spans all three ARDEC parcels) come through Intersect fine as single multipart output rows. So disconnected geometry alone doesn't cause row-splitting.

**Actual root cause, confirmed by direct comparison:** `PRC_Official_26913` still had **two rows** (`OID=1`, `OID=2`) at the time Clip Soils ran — despite the user having dissolved `PRC_Official_unproj` (multiple times, by their account) into one row beforehand. Cause: `Batch Project Layers.ipynb` cell-0 skips reprojecting any layer whose `_26913` output already exists (`if arcpy.Exists(out_fc): ... continue`). Since `PRC_Official_26913` had already been created once *before* the dissolve, every subsequent cell-0 run silently skipped regenerating it from the newly-dissolved `PRC_Official_unproj` — the stale two-row version just sat there. Clip Soils then correctly intersected the SSURGO data against a genuinely two-row boundary, producing one output row per boundary row for any mukey overlapping both.

**Fix applied and confirmed working by user:** delete `PRC_Official_26913`, re-run cell-0 (now correctly regenerates as one row from the dissolved source), re-run Clip Soils. WIA now comes through as a single row.

**Takeaway for future multi-parcel stations:** cell-0's skip-if-exists behavior means re-dissolving/re-editing a `_unproj` boundary after its `_26913` output already exists will *silently* not propagate unless the stale `_26913` (and any downstream `_Soils`/`_Soils_WM`) is deleted first. Not just a PRC quirk — applies to any station's boundary if it's edited after the first successful project run.

**The real finding:** while working through the display-field error, realized the `"ALL"` attribute join in `Clip Soils to Updated Boundaries.ipynb`'s `Intersect` call pulls through *every* field from the boundary side too — including full assessor/parcel data where the boundary source was county parcel data (owner names, account numbers, mailing addresses, land values, etc.). Cleaning at the source means `_Soils`, `_Soils_WM`, and any future export all inherit clean data automatically — no separate cleanup step needed downstream, and the original assessor shapefiles remain the only place that data legitimately exists.

## Part 10: AGOL publish — error cascade, and the real culprit (working map vs. publish map)

Long troubleshooting thread getting `Share → Overwrite Web Layer` to actually succeed against the live `CSU_AES_Soils` hosted FeatureServer. Several distinct errors surfaced, most of which turned out to be downstream symptoms of one root cause discovered at the very end.

**Individual errors chased down (roughly in order):**
- **00241 — display field set to `Shape_Length`** (9 layers): fixed via Layer Properties → **Display** tab (not "General" — got this tab name wrong on the first guess) → set to `musym`/`muname`. Turned out 00241 can also come from **labeling** (label class SQL query) or **symbology** (primary symbology field), not just Display Field — worth remembering if this recurs, since fixing Display Field alone didn't fully resolve it this time (the real reason was something else — see below).
- **00374 — unique numeric IDs not assigned**: the map-level toggle (`m.allowAssigningUniqueNumericIds = True`, set via notebook cell earlier) isn't sufficient by itself. Confirmed via Esri docs: each individual layer also needs an explicit **Layer ID** set — right-click layer → Properties → General tab → "Layer ID" field → type an integer matching the existing published service's ID for that layer. Live service IDs (read from `aes-data.html`'s `STATIONS` config): `ARDEC=23, ARDEC South=24, AVRC=25, ECRC=26, GVRC=27, OMRC=28, PRC=29, RMRC=30, SLVRC=31, SWCRC=32`. (First doc fetch gave an inaccurate paraphrase of these steps — "click the number next to the layer" isn't a real UI gesture — corrected by fetching the more specific `assign-layer-ids` doc page directly.)
- **00210 — duplicate layer ID after manual assignment**: expected side-effect of the above — some *other* layer in the map (not one of the ten `_Soils_WM` layers) had an auto-assigned ID landing in the 23–32 range. Fix: hover the error → Options → Change General Layer Properties → bump the colliding layer to something outside the reserved range (100+ is fine, doesn't need to mean anything since it's not being published).
- **Group layer (`WCRC`) not supported for web feature layer**, plus bare `ARDEC` and `Colorado Border` layers also showing the Shape_Length display-field error despite not being intentionally selected for sharing.

**The actual root cause**, found only after noticing unrelated/unselected layers kept getting flagged: the Analyzer was being run against the **wrong map**. This project deliberately maintains two maps — "AES" (the working map where all of today's pipeline work happened, containing every intermediate/reference layer from the whole session) and **"CSU - AES"** (a dedicated, clean, publish-only map). The intended workflow is to copy the finished `*_Soils_WM` layers over to "CSU - AES" and run Share/Overwrite *from that map* — not from "AES," which naturally contains everything and so gets fully validated by the Analyzer regardless of which layers are checked in the share-selection list. This is the same two-maps setup that caused symbology confusion back on `2026-07-01.md`; worth remembering this distinction exists and matters for *any* future publish, not just this one.

Once the ten `_Soils_WM` layers were copied to "CSU - AES" and the Overwrite was run from there, the `WCRC`/`ARDEC`/`Colorado Border`/stray-display-field errors all disappeared at once, confirming the diagnosis.

**One non-issue along the way, worth remembering:** a yellow warning icon reading "Layer name for ID # has changed" is *not* an error — it's informational, noting the display name stored on the already-published sublayer differs from the current local layer name (e.g. `"ARDEC Soils"` on the live service vs. `ARDEC_Soils_WM` locally). Since the IDs matched (which is what actually matters for Overwrite to target the correct sublayer), this was expected and not something to "fix" by renaming layers back.

World Imagery / Hybrid Reference Layer "data source not supported" was correctly recognized as expected throughout — Esri's own basemap tiles can't be republished as a web feature layer, by design.

**Publish completed successfully** at the end of this session — `CSU_AES_Soils` is now live with the corrected PRC boundary, deduplicated mukeys, and assessor-data-free attribute tables across all ten stations.
