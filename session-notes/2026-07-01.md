### GIS workflow notes from this process
- Standard flow per station: select parcel(s) → Export Features → Merge (if multi-parcel) → Dissolve (Create multipart features checked; non-touching parcels stay bundled in one output, nothing lost).
- KMZ preferred over SVG when a county offers both — SVG has no georeferencing.
- Standalone `.geojson` sometimes fails ArcGIS Pro's "Add Data" drag-and-drop even when perfectly valid (confirmed via byte-level check: no BOM, not truncated) — known Pro reliability quirk. Fix: use the **JSON To Features** geoprocessing tool instead.
- SLVRC has two parcels (East/West); Rio Grande County's export choice should be **GeoJSON**, not "Item" (Item just creates an ArcGIS Online hosted item, not a downloadable file).

## Projection strategy

App's published layers use **EPSG:26913** (NAD83 UTM 13N) for area-calculation accuracy — documented in `aes-data.html`. Decided the three westernmost stations (GVRC, OMRC, SWCRC) should be computed in their **geographically native EPSG:26912** (UTM 12N) instead, for better area accuracy, since they sit west of the 108°W zone boundary. RMRC (near Hotchkiss, ~107.7°W) is geographically just inside Zone 13N despite being grouped with the other "Western Colorado Research Center" sites, so it stays in the 26913 group.

Initially assumed 26913/26912 was the *final* display projection — corrected mid-session: `index.html` never displays boundary polygons directly (`goToStationExtentEnsuringVisibility()` just calls `queryExtent()` on the `_Soils` feature layer itself), so the boundary layers' only job is defining the clip; only the `_Soils` layers need an eventual EPSG:3857 (Web Mercator) version for the live map, which the existing `Batch Project Layers.ipynb` cell already handled.

## Notebook work: `Export Boundaries for R Pipeline.ipynb` (new)

Discovered mid-session that there are **two entirely separate boundary pipelines** that don't talk to each other:
1. The ArcGIS-side one above, living entirely in `Master List.gdb`.
2. `build_all_profiles.R` (which actually drives `all_stations_profiles.json`, i.e. what `aes-data.html` displays) reads its **own independent copy** of boundary shapefiles from `.../AES_soil_profiles/data/boundaries/{station}.shp`, and does its own bbox-filter + `st_intersection` against a local SSURGO geopackage. This mismatch between the two boundary copies is exactly why the musym 56 gap (see below) existed in the first place.

Built a new notebook to bridge them: copies each finalized `_Official_26913`/`_26912` feature class out as a correctly-named `{station}.shp` into R's boundary folder, overwriting the stale placeholders. Confirmed by reading `build_all_profiles.R` in full that **no R code changes are needed** — its station list already matches exactly, and it reprojects any input CRS automatically via `st_transform(mu_crs)` right after reading, so the 26913/26912 split is a non-issue there.

User raised a good point near the end: why doesn't R just consume the already-clipped `_Soils` layers instead of maintaining its own redundant copy? Correctly identified this duplication as the root mechanism behind the musym 56 gap. Not acted on — flagged as a legitimate future refactor, with the caveat that R also needs relational component/chorizon data via SQL + `fetchOSD()` that a GIS polygon attribute table likely can't fully replace (unverified whether `mupolygon_all_joins_26913`'s own fields already cover this — that layer was confirmed to have been built manually via ArcGIS Pro's GUI, not scripted).
